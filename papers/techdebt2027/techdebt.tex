\begin{abstract}
Code duplication is a well-known source of technical debt, but little is known about how developers of large, long-lived systems actually pay it back. We investigate code deduplication in the Linux kernel, where changes are publicly reviewed on mailing lists before they reach the upstream repository (mainline). Our goal is to understand how clones are refactored in practice, which refactoring techniques developers apply, and how maintainers receive deduplication patches. We combine two sources of evidence. First, through an ethnographic study, we submitted deduplication patches to the AMDGPU and IIO subsystems and followed their review process. We qualitatively analyzed 30 contributions, classifying the refactoring techniques applied and discussed with maintainers according to Fowler's refactoring catalog. Second, we mined the clone refactoring patches found in a sample of kernel mailing-list threads and quantitatively analyzed XX contributions to measure how frequently each technique is applied and to identify whether additional techniques emerge.

\section{Introduction}\label{sec:introduction}

Developers often reuse existing code by copying, pasting, and adapting it, a practice that accompanies the evolution of large, long-lived systems~\cite{kumar2016managing}. The resulting duplication is a well-known code smell~\cite{fowler2018refactoring} and, as such, a form of technical debt~\cite{kruchten2012technical}.
However, cloning can be a deliberate design choice, as when developers fork existing code to support variations in hardware or platforms, or replicate boilerplate that the programming language cannot express in a more abstract form~\cite{kapser2008cloning}. Even so, duplicated code places a burden on maintenance. A change to one copy, such as a bug fix, must be propagated to all the others, and inconsistent changes to clones that should evolve together are a known source of faults~\cite{juergens2009clones,li2006cpminer}.

\section{Related work}\label{sec:related_work}

Wang and Godfrey~\cite{wang2014intentional} searched the commit history of the Linux kernel for messages that mention ``duplicated code'' and found 348 commits, which they call intentional clone refactoring. After matching these commits against clone detection results, they found that clones associated with intentional clone refactoring account for fewer than 1\% of all detected clone changes. According to the authors, this result suggests that most clone refactoring is not mentioned in commit messages. The authors argue that intentional clone refactoring data may reveal how clones are managed in practice, and that the ways of removing duplication are a key to this understanding. However, they do not investigate these patterns, and their dataset also includes commits that create or modify duplicated code. Our work addresses this point by examining only contributions that remove duplication and identifying the technique each one applies. In our second step, we follow a similar idea of relying on what developers state about their own changes, but we manually analyze patch series from the kernel mailing lists instead of matching keywords in commit messages.

Other studies proposed ways of reducing duplication in the kernel. Kadav and Swift~\cite{kadav2012drivers} found that 8\% of all Linux driver code is very similar to other driver code and, after inspecting the clusters of similar functions, suggested three methods to reduce it: procedural abstraction, which moves the shared code to a library, better support for multiple chipsets in a single driver, and table-driven programming. Yu and Ramaswamy~\cite{yu2008modularity} classified 903 Linux clone sets into three categories and suggested a treatment for each one: library functions, aspects, or leaving the clones unchanged. Kumar et al.~\cite{kumar2016bigclones} took a different path and kept the kernel code
as it is, representing duplicated files and directories as templates in a layer above the code, which eliminated 30--50\% of the code in the groups they studied. In these three studies, the techniques come from researchers who analyzed the code from the outside, and none of them was submitted to kernel maintainers. In contrast, we study techniques that were applied in real patches
and accepted in code review.

The work closest to ours is the study by Arcanjo et
al.~\cite{arcanjo2026repeat}, which this paper extends. The authors detected duplicated functions in the AMDGPU and IIO subsystems, submitted deduplication contributions, and analyzed 13 patch series interactions with maintainers. They identified
four factors that lead maintainers to tolerate duplication, and therefore to reject its removal: driver-forking, readability, integration overhead, and performance. That study explains when and why deduplication is rejected or accepted. It names the refactoring used in each contribution, such as moving identical functions to a shared library, parameterizing a method, or extracting helpers, but only as part of the account of each review, without characterizing or comparing these techniques. We follow the same participant observation approach and add the patches submitted by the group over 2026. Our focus, however, is on the accepted contributions and on the techniques they apply. We also go beyond the patches of our own group and analyze additional samples from the kernel mailing lists, to check whether the same techniques appear there or whether new ones emerge.

\section{Methodology}\label{sec:methodology}

This study extends the work of Arcanjo et al.~\cite{arcanjo2026repeat} with a new focus, which is to understand how deduplication is done in the Linux kernel and to characterize the techniques applied in the patches. To find the
duplications to be removed, we used the same tool as that study, ArKanjo~\cite{arcanjo2025arkanjo}, a command-line tool that detects duplicated
functions in large C codebases and works more accurately with \mbox{Type-1} and \mbox{Type-2} clones. We also followed its methodology, with a complete participant observation, in which we submitted
deduplication patches ourselves, followed by a participant-as-observer observation, in which students of a university
course~\cite{tadokoro2025guidelines} also submitted deduplication patches. In 2026,
17 new patch series were submitted to the AMDGPU and IIO subsystems, targeting \mbox{Type-1} and \mbox{Type-2} duplications found with similarity thresholds of 90\% and 100\%. Together with the 13 patch series from the previous study, our analysis covers 30 patch series.
Throughout this paper, we broadly refer to these development activities as developer ``contributions'', while we technically analyze and count them as individual ``patch series'' (which may consist of a single patch or multiple patches) in our evaluation.
Then, to validate the deduplication techniques we found, we analyzed a sample of threads from four kernel mailing lists: \mbox{amd-gfx},
\mbox{linux-iio}, \mbox{iommu}, and \mbox{linux-i2c}. Since these contributions were sent outside the course, this sample broadens our corpus and allows us to check whether their techniques match the ones we observed or whether new techniques appear.

\subsection{Participant Observation}\label{subsec:participant-observation}

In the complete participant observation, three authors of this paper submitted six of the 17 new deduplication patch series, two to the AMDGPU
subsystem and four to the IIO subsystem. With these interactions, we sought to understand how the contribution process to the kernel works and to map the interactions with maintainers. For each
patch series, we followed the same process. First, we used ArKanjo to detect duplications in the two subsystems. Then, we analyzed the duplicated code and chose a refactoring technique to remove the duplication. Finally, we submitted the patch series to the subsystem mailing list and analyzed the interactions with the maintainers during the review.

\subsection{Reusing and Simplifying Existing Code}\label{subsec:reusing-and-simplifying}

We classified techniques TEC3, TEC5, and TEC6 as those that reuse or simplify existing code. Since the
kernel is a free software project that has been available for more than 30 years, there is often no need 
to create something new, as the result one wants to achieve is already available for use. Of the 30 patch series, 
only 11 fall into this group, that is, about 37\%.

When the duplicated function already exists in another hardware version,the reuse happens through 
the function pointer tables that each version uses to register its callbacks. Group G15, for instance, found that
\texttt{jpeg\_v3\_0} had an interrupt handler identical to the one in \texttt{jpeg\_v2\_0} and, 
following a maintainer's suggestion, simply pointed \texttt{jpeg\_v3\_0\_irq\_funcs} to the previous version's
function, removing the duplicate. In this case, no new code is needed: the refactoring consists of changing 
which function the table references.

In the TEC3 patch series, the duplicated code was usually a sequence of \texttt{switch} cases that mapped 
values in a very similar way. Groups G11, G18, and G12 replaced these \texttt{switch} cases 
with lookup tables, so the mapping is described as data instead of control flow. However, this change is 
not always seen as an obvious improvement. In G18, a maintainer questioned whether the new table 
was really less prone to errors and concluded that the advantage was ``rather the reduction in verbosity''. 
Group G5 took a different path: since the two duplicated functions returned opposite values, one of 
them was replaced by the negation of the other. In this case, the refactoring does not change the way we see 
the \texttt{switch} statement, but changes how the existing logic is expressed, and whether it is better depends 
on how readable the result is.

Besides that, deduplication does not always mean creating a new function. Group G19 applied TEC6 and 
went in the different direction by following the maintainers' comments, it removed helper functions and incorporated 
their logic directly where they were used. One of the maintainers noted that it was ``a helper that doesn't necessarily 
add much value''. Here, the duplication was in the helper itself, and removing it made the code simpler 
(according to the maintainer himself) . This shows that, in the kernel, a helper function is not always positive, and 
it is necessary to examine case by case.


\subsection{Introducing New Abstractions}\label{subsec:new-abstractions}

The remaining techniques, Extract Function, Parameterize Function, and Pull Up Method, are those that 
somehow add a new layer to the code: a new function, a function moved to a shared file, or a more general 
function that combines the duplicated ones through parameters. These techniques were the most common 
in our corpus, with 19 of the 30 patch series, that is, about 63\%.

In TEC1, the main difference between the two subsystems is where the extracted function is placed. 
In the IIO patch series from 2025 (groups G2, G8, and G9), the duplicated functions belonged to the 
same driver, and the common function stayed in the same file. In AMDGPU, all Extract Function patch series dealt 
with functions duplicated across different hardware versions, a consequence of the driver forking (T1) practice already 
observed in the subsystem~\cite{arcanjo2026repeat}. In these cases, the common function was moved to the generic layer of 
the IP, such as \texttt{amdgpu\_gfx.c} (G16, G17, and G22) and \texttt{amdgpu\_gmc.c} (G20 and G21), or to a 
new file created for this purpose (G13). This shows that, in AMDGPU, extracting a function also means 
choosing a place for it in the driver architecture, and, as discussed in Section~\ref{subsec:how-review-reshapes-the-refactoring}, 
new files proposed by the patch series were removed during review.

Being identical, however, is not enough for a function to be moved to the generic layer. In G17, the 
maintainers agreed that there was nothing specific to the hardware generation in the function and recognized 
that it was ``probably just copy and pasted over when we brought up gfx12''. In G20, the duplicated functions 
were also identical, but the maintainer stated that they were intentionally kept separated for each generation. 
In practice, what decides if the code can be shared is whether its behavior belongs to a single hardware generation 
or to all of them, which the textual similarity alone does not show.
