\begin{abstract}
Code duplication is a well-known source of technical debt, but little is known about how developers of large, long-lived systems actually pay it back. We investigate code deduplication in the Linux kernel, where changes are publicly reviewed on mailing lists before they reach the upstream repository (mainline). Our goal is to understand how clones are refactored in practice, which refactoring techniques developers apply, and how maintainers receive deduplication patches. We combine two sources of evidence. First, through an ethnographic study, we submitted deduplication patches to the AMDGPU and IIO subsystems and followed their review process. We qualitatively analyzed 30 contributions, classifying the refactoring techniques applied and discussed with maintainers according to Fowler's refactoring catalog. Among our findings, we highlight that maintainers tend to resist deduplications that introduce new abstractions more than the reuse of existing ones. Second, we mined patches from the mailing lists for clone refactorings arriving in a sample of 71 contributions; we quantitatively analyzed the techniques applied to validate and expand the findings from our ethnographic study. Extract Function was the most frequent technique in both datasets, suggesting that even simple refactoring techniques can yield valuable contributions to a system as complex as the Linux kernel. By analyzing 101 contributions, this study provides empirical evidence of the refactoring techniques used to remove code duplication in the Linux kernel, bringing insight on how these techniques relate to the acceptance of deduplication during its review process.
\end{abstract}

\section{Introduction}\label{sec:introduction}

Developers often reuse existing code by copying, pasting, and adapting it, a practice that accompanies the evolution of large, long-lived systems~\cite{kumar2016bigclones}. The resulting duplication is a well-known code smell~\cite{fowler2018refactoring} and, as such, a form of technical debt~\cite{kruchten2012technical}, whose cost is paid during maintenance. A change to one copy, such as a bug fix, must be propagated to all the others, and inconsistent changes to clones that should evolve together are a known source of faults~\cite{juergens2009clones}.

Linus's Law states that ``given enough eyeballs, all bugs are shallow''~\cite{raymond1999cathedral}.
In the Linux kernel, part of this examination takes place in a well-established and rigorous review process, in which patches are publicly reviewed on mailing lists before integration and only about a third of them are eventually accepted~\cite{jiang2013patch}.
Extending this reasoning to technical debt, such a process would also be expected to catch duplicated code before it is merged, leaving few opportunities for simple deduplication.
This expectation, however, does not seem to hold, as duplicated code, from small fragments to entire files and directories, is still found in the kernel~\cite{kumar2016bigclones}.

In this context, we investigate how duplication debt is repaid in practice in the Linux kernel, examining which refactoring techniques developers use to remove clones and how maintainers respond to deduplication patches during review.
To this end, we draw on two sources of evidence.
First, we conducted an ethnographic study based on participant observation in the AMDGPU and IIO subsystems, in which we submitted deduplication patches ourselves and also followed the review of patches submitted by students during a university course. We qualitatively analyzed these 30 contributions, classifying, according to Fowler's refactoring catalog~\cite{fowler2018refactoring},  the techniques they applied. Second, we mined the kernel mailing lists for clone refactorings, using a broad regular expression over duplication-related keywords that retrieved 207 threads, which we manually analyzed to retain only those actually concerned with code duplication, resulting in 71 threads. We then quantitatively analyzed the refactoring techniques applied in these contributions, using the same catalog, to validate and expand the findings of the ethnographic study.

In the ethnographic study, maintainers were more reluctant to accept deduplications that introduced new abstractions than those that reused abstractions already available in the kernel.
In both sources, Extract Function was the most frequently applied technique. These findings suggest that deduplication is a suitable entry point for contributors with less experience in the kernel, since, although it requires understanding the duplicated code and its context, it involves relatively low complexity and can often be addressed with simple refactoring techniques. They also indicate that, despite its rigorous review process, the Linux kernel still carries duplication debt that is cheap to repay. With this study, we aim to draw attention to the duplication debt that remains to be repaid in the Linux kernel and to offer insights into how it can be addressed.

\section{Related work}\label{sec:related_work}

Wang and Godfrey~\cite{wang2014intentional} searched Linux kernel commit messages for ``duplicated code'' and found that these intentional clone refactorings account for fewer than 1\% of the clone changes detected in four subsystems. Choi et al.~\cite{choi2012clones} examined how clones are refactored by comparing versions of three open-source Java projects, and found that refactored clone pairs were mostly handled with two patterns from Fowler's catalog, Replace Method with Method Object and Extract Method. Unlike these studies, which infer clone refactorings from commit messages or code versions, we examine deduplication patches together with their review, both from within the community, by submitting and following patches, and on the kernel mailing lists, where the complete discussion of each contribution is available rather than only its commit message.

Other studies proposed ways of reducing duplication in the kernel.
Kadav and Swift~\cite{kadav2012drivers} found that 8\% of driver code is very similar to other driver code and suggested procedural abstraction, better support for multiple chipsets, and table-driven programming to reduce it. Yu and Ramaswamy~\cite{yu2008modularity} classified 903 clone sets into three categories and suggested library functions, aspects, or no change, depending on the category. Kumar et al.~\cite{kumar2016bigclones} represented duplicated files and directories as templates in a layer above the code, reducing redundant code by 30--50\% in the groups they studied. These techniques were proposed by researchers who analyzed the code from the outside, and none of these studies reports submitting the changes to kernel maintainers. In contrast, we study techniques applied in real patches submitted to kernel maintainers.

Anonymized Authors [x] submitted deduplication patches to the AMDGPU and IIO subsystems and, from 13 patch series, identified four scenarios under which maintainers tolerate duplication, namely driver-forking, readability, integration overhead, and performance. In that study, the refactoring used in each contribution appears only as part of the account of each review, without being characterized or compared. We follow the same participant observation approach and expand the sample to 30 contributions, focusing on the techniques they apply and on how maintainers receive them. We also analyze contributions from the kernel mailing lists, to check whether the same techniques appear or whether new ones emerge.

\section{Methodology}\label{sec:methodology}

To understand how code duplication is removed in the Linux kernel, we combined two complementary sources of evidence. Through participant observation, we followed deduplication patches from their submission through their discussion with maintainers, which gave us an in-depth view of how these contributions are received. Through mining the kernel mailing lists, we collected deduplication contributions beyond those we followed, which allowed us to check whether the techniques observed in the first source also appear in a broader sample. We then classified the refactoring techniques in both samples according to Fowler's catalog~\cite{fowler2018refactoring}, analyzing the first qualitatively and the second quantitatively. The following subsections describe each of these steps in detail.

\subsection{Participant Observation}\label{subsec:participant-observation}

We adopted an ethnographic approach to observe how deduplication patches are received from within the kernel community, following each decision as it happens rather than reconstructing it afterwards from code artifacts.
We conducted this participant observation in the IIO and AMDGPU subsystems of the Linux kernel, adopting two of the observer roles described by Gold~\cite{gold1958roles}, complete participant and participant as observer. In both roles, the duplications addressed by the patches were identified with ArKanjo~\cite{arcanjo2025arkanjo}, a tool for detecting function-level code duplication in the Linux kernel. We consider each patch series, including all its versions, as one contribution.
In total, we qualitatively analyzed 30 contributions, 13 of which had been analyzed in a previous study~[Anonymized] (C1 to C13) and 17 of which are new (C14 to C30), all listed in Table~\ref{lbl:patches-summary}.

In the complete participant role, we contributed to the kernel ourselves, selecting duplications reported by the tool, preparing deduplication patches, submitting them to the subsystem mailing lists, and interacting with maintainers during review, which resulted in 6 of the 17 new contributions.

In the participant as observer role, we followed contributions submitted by students during a university course in the first semester of 2026.
We mentored them during the submission process and followed the reviews they received from maintainers. The students submitted the remaining 11 new contributions.

\subsection{Mailing Lists Mining} 

To check whether the techniques observed in the participant observation also appear in contributions beyond those we followed, we mined e-mails from the kernel mailing lists available in the LKML5Ws dataset~\cite{passos2026lkml5ws}.
We used four lists, IIO, AMDGPU, IOMMU, and I2C.

Since the dataset stores individual e-mails, we first reconstructed the discussion threads, linking each e-mail to its parent through the \texttt{In-Reply-To} header, falling back to the last identifier in the \texttt{References} header when \texttt{In-Reply-To} was missing or pointed to a message absent from the dataset.
We then grouped the linked e-mails into threads,  and ordered the messages of each thread by date.

Based on the vocabulary that contributors and maintainers used to discuss duplication during the participant observation, we built a regular expression to filter threads. Among the threads that matched it, we discarded those authored or answered by our group or by the course students and randomly selected 220 of the remaining ones. 13 threads were excluded, 11 that contained only pull requests, which summarize patches discussed in other threads and include neither diffs nor discussion, 1 that was already part of another thread in the sample, and 1 whose duplication terms appeared only in text quoted from other messages, leaving 207 threads.

Two authors independently labeled each of the 207 threads as related or not to code duplication, and resolved disagreements by consensus. This resulted in 71 threads related to code duplication, 25 from IOMMU, 18 from AMDGPU, 15 from IIO, and 13 from I2C, which form the sample we analyzed. The labeled threads and the details of the sample selection are available in our replication package.\footnote{\texttt{https://anonymous.4open.science/r/linux-refactor\allowbreak i\allowbreak n\allowbreak g\allowbreak s-2E24/}}

\subsection{Refactoring Technique Analysis}\label{sec:technique_analysis}

We classified the refactoring techniques according to Fowler's catalog~\cite{fowler2018refactoring}, starting with the participant observation contributions. For each of the 30 contributions, we examined the code changes in its patches and compared them with the descriptions and examples of the refactorings in the catalog, assigning the technique that best matched the changes.
We then analyzed these contributions qualitatively, relating the technique applied in each one to how maintainers received it. Next, we applied the same classification to the 71 mailing list contributions. Some of these patch series addressed more than one change, and in these cases we assigned a technique to each change, so that a single contribution may account for more than one technique.
Finally, we analyzed this sample quantitatively, counting how often each technique was applied.

\section{Results and Discussion}\label{sec:results-and-discussion}

We classified the 30 patch series for code deduplication according to the refactoring techniques they apply, using Fowler's 
catalog~\cite{fowler2018refactoring}. Five techniques appear in our corpus (Table~\ref{lbl:patches-summary}): Extract Function is the most frequent,
applied in 10 patch series, followed by Parameterize Function with 6, Substitute Algorithm with 5,
Replace Inline Code with Function Call with 4, and Pull Up Method with 3.
These techniques differ in whether they reuse code that already
exists in the kernel or introduce a new abstraction, and in where the shared code is placed. In the 
following paragraphs, we use representative contributions to describe how each technique is applied in the 
kernel, and Section~\ref{subsec:how-review-reshapes-the-refactoring} discusses how code review shaped the final form of the submissions.

Most contributions were small. The median contribution removed $31$ lines of code, and 27 of the 30
removed fewer than $100$. Three contributions (C9, C11, and C29) even added between $1$ and $4$ lines.
Large series were not a barrier (the three largest, C1, C2, and C17, were accepted), but very small
ones were dropped more often; five of the 12 dropped series removed at most $10$ lines, compared with
two of the 18 accepted.

\subsection{Ways of removing a clone}\label{subsec:reusing-and-simplifying}

The techniques that reuse and simplify existing code, Replace Inline Code with Function Call and Substitute 
Algorithm, were also the ones most easily accepted: 8 of their 9 contributions were accepted, 
against 9 of the 19 contributions that introduce a new abstraction\footnote{C3 and C24 were not assigned a deduplication technique and are not counted in either group.}.
We describe the techniques grouped by how they remove the clone: extracting the repeated code,
reusing what already exists, substituting the algorithm, and parameterizing similar functions.

Extract Function, the most frequent technique, only requires moving the repeated fragment into a new
function and calling it from each copy. In IIO, duplicated functions were part of the same driver,
so the new function simply remained in the same file. In AMDGPU, the copies were spread across hardware
versions due to driver-forking (T1), and the new function was placed in a generic layer
already shared by these versions, such as \texttt{amdgpu\_gfx.c} and \texttt{amdgpu\_gmc.c}. 
In C22, this was enough to remove the duplication: the maintainers agreed that nothing 
in the function was specific to a hardware generation, one of them speculated that it was ``probably just 
copy and pasted over when we brought up gfx12'', and accepted the patch series. 
In C25, the duplicated functions were also identical, but the maintainer stated that they
were intentionally kept separated for each generation, and the patch series was rejected. Both
duplications derive from driver-forking (T1), but only the first appears to have been accidental. Thus, extracting the
function is the simple part of the task, while what requires attention from the contributor is checking
whether the duplication was intended.

Extract Function was not always the easy case. C4 was dropped because the new helper was questioned, and the gain was seen as too small to justify the upstreaming effort (T2, T3). The status ``Dropped'' therefore covers explicit rejection as well as series that stopped.

Pull Up Method, in turn, moves a whole duplicated function, rather than just a fragment, to a shared
place and can remove a large amount of code with a simple change. In C2, the \texttt{hpd\_ack()} function
was duplicated, with minimal changes, in the drivers of several GPU generations, a consequence of driver
forking (T1)~[Anonymized], and the contributor replaced these copies with two library functions
that covered all cases, which was accepted. In C28, however, the same technique was rejected precisely
because of driver-forking (T1): one maintainer initially accepted the patch series, but another dropped it,
arguing that keeping the code independent for each generation had avoided problems in the past.

Replace Inline Code with Function Call removes the duplication without writing any new code, since
the function that replaces the repeated code already exists and the contributor only needs to call it.
Noticing that an existing function can replace the repeated code, however, requires some
investigation of the subsystem, and maintainers can point it out during review. In C20, the contributor 
found that the interrupt handler of \texttt{jpeg\_v3\_0} was identical to the one in 
\texttt{jpeg\_v2\_0} and, following a maintainer's suggestion, pointed the callback table of the 
newer version to the older function, removing the duplicate. This duplication
is a consequence of driver-forking (T1), as the newer hardware version kept its own copy of a function
already implemented for the previous one. In IIO, C12 applied the same technique by replacing 
duplicated functions with calls to SPI helpers already available in the kernel. 
The only exception was a single occurrence that reads large buffers, which, at the maintainer's 
request, kept using an internal helper since the generic ones would harm performance (T4)~[Anonymized].

Substitute Algorithm was also simple to apply when the duplicated code was a sequence of \texttt{switch}
cases that mapped values in a very similar way. In these cases, the contributor only had to list the
values of each case in a lookup table, so that the mapping is described as data instead of control flow.
In C23, a maintainer questioned whether the new table was really less prone to errors than the \texttt{switch}
cases, but concluded that its advantage was ``rather the reduction in verbosity'', and the patch series
was accepted. The same replacement also scales to larger changes, as in C17, the largest contribution
in our corpus, which was accepted in its first version. Since the gain of this technique comes mostly in
readability (T2), the same scenario can also work against it: in C13, the maintainer judged that the
code reduction did not compensate for the loss of readability, and the patch series was rejected.

Parameterize Function, which appeared only in IIO, merges similar functions into a single one that
receives their difference as a parameter. Only 2 of the 6 series that used it were accepted. In C6, the
functions differed only in the type of \texttt{struct}, so a generic \texttt{struct} was passed as a parameter,
and the patch was accepted in its first version, also fixing a bug. The dropped series were questioned on
readability and gain rather than on correctness (T2). In C5, a maintainer judged that the reduction was not significant
enough to justify the more complex code. In C9, the main objection was that wrapping the code scattered what used
to be close together, so the reviewer had to look at the function and at where the value was set. In C29,
the common function received a boolean parameter (\texttt{is\_accel}) and several levels of pointers, and a maintainer
replied: ``Here and below the function is completely uglified. Even kernel documentation suggests to avoid
bool parameters like this''. Another maintainer noted that a deduplication that adds lines, as C29 did, should
be questioned (T3). In our cases, parameterizing worked when the parameter captured the only difference
between the functions, as in C6, and not when it became a flag or moved the point where the behavior is
decided away from the reader.

Overall, the techniques we observed are well known and result in localized changes. What the reviews add is why a clone was not removed: it was kept on purpose (T1), the result would be harder to read (T2), the gain did not justify the integration effort (T3), or the shared code would sit on a performance-sensitive path (T4). These scenarios are not fixed rules, since maintainers of the same subsystem disagreed on them, as in C28. Table~\ref{tab:recipes}  relates each technique to an accepted case and to the concerns raised in the others. Moreover, code review often reshapes the refactoring itself, showing how the maintainers' knowledge of the subsystem can influence the final form of a contribution.

\subsection{How Review Reshapes the Refactoring}\label{subsec:how-review-reshapes-the-refactoring}
% Talvez falar sobre o baixo numero de patches da categoria "Reusing and Simplifying Existing Code": 
% Talvez seja necessário ter um maior conhecimento do subsistema para fazer um INLINE_FUNCTION e um REPLACE_INLINE
A recurring pattern across some contributions is that maintainer review
can redirect a patch, changing the abstraction scope, the refactoring
technique, or both. Three contributions illustrate each of these outcomes.

In C18, the first version consolidated the duplicated functions into a new 
file, \texttt{amdgpu\_common.c}, intended to group functions shared across 
the subsystem. A maintainer rejected this layout: ``Please don't when they 
are functional identical then move them a layer up instead of messing up the 
backends.'' He then argued that each function would fit better in a 
different, already existing layer. Although the refactoring technique 
remained the same across all revisions, the abstraction scope shifted to 
follow the layering conventions already established in the subsystem.

In C27, the opposite happened. The scope was kept, but the technique 
changed. The contributor initially proposed a single generic function in 
\texttt{amdgpu\_gfx.c} to replace \texttt{gfx\_v11\_0\_handle\_priv\_fault} 
and \texttt{gfx\_v12\_0\_handle\_priv\_fault}, arguing that the two were 
identical. In the first review, a maintainer pointed to a specific code 
fragment and noted ``Even when they are identical on gfx11 and gfx12 this 
decoding here is HW specific and doesn't belong here''. The target layer was 
not questioned, and \texttt{amdgpu\_gfx.c} remained the destination across 
all revisions. As a result, the contributor switched from Pull Up Method to Extract Function. Therefore, only 
the generation-independent part was moved to \texttt{amdgpu\_gfx.c}, while 
the hardware-specific decoding remained in each generation's own function.

In C19, review changed both the scope and the technique. The first version 
made \texttt{jpeg\_v5\_0\_1.c} and \texttt{jpeg\_v5\_0\_2.c} share a common 
interrupt routine placed in a new file, \texttt{jpeg\_v5\_0\_interrupt.c}. 
This proposal was dropped in the first review because the routine was not 
common to the whole family and the maintainer pointed ``This is not common to 
jpeg v5.  \texttt{jpeg\_v5\_0\_0.c} has a different interrupt handler''. The maintainer then 
suggested a narrower alternative: ``I would just make the implementation in 
\texttt{jpeg\_v5\_0\_1.c} non-static and then just use it directly in 
\texttt{jpeg\_v5\_0\_2.c}''. The duplication was still removed, but the scope was 
changed from a family-wide file to the two drivers that actually share the 
behavior, and the technique changed accordingly, to Replace Inline Code with Function Call.

Although the outcomes are different, the main concern is the same in all three cases. 
The shared code either did not belong to the proposed layer or
did not apply uniformly to every component that layer serves. These cases do not fit the
four scenarios proposed in the previous study~[Anonymized]. They are adjacent to T1, since
the objections derive from hardware-specific code, but the maintainers did not defend the
independence of the drivers as such. In C19 and C27, code that looked identical was not
shared knowledge: another driver of the family has a different handler, and part of the
decoding is hardware-specific. In C18, the objection concerned which existing layer should
hold the code. Nor did the maintainers invoke readability (T2), integration overhead (T3),
or performance (T4). This leads to a fifth scenario (T5): maintainers may reject or redirect
a deduplication when the duplicated code does not share an appropriate abstraction boundary.
Consolidating such code into a shared layer can be considered inappropriate when the behavior
does not apply uniformly to every component that the layer serves.

Extract Function was the most frequent technique overall in both datasets, accounting for a third of the applications in our corpus and remaining the most common in the mailing lists. The techniques applied in our submissions also accounted for most of the applications in the broader sample, including those related to the IOMMU and I2C subsystems, where we did not submit patches.

The mailing lists also revealed techniques that none of our submissions applied, namely Remove Dead Code, Pull Up Field, and Slide Statements. Pull Up Field moves fields repeated across structures to a shared one. Remove Dead Code was used both for unused code and for implementations that became redundant after equivalent functionality was made available elsewhere in the kernel, such as in a core layer. ArKanjo reports function-level clones, so changes to fields and statements fall outside its reach; in some cases, they appear as preparatory steps for a later extraction.

Series without a catalog technique show that deciding whether to remove duplication is part of the task. Some introduced shared code to prevent future duplication rather than to remove an existing clone, and others tolerated duplication across distinct drivers, where abstracting would cost more than it would gain. In other cases, maintainers prevented duplication at its origin, asking the contributor to build on an existing driver instead of adding a new one. These cases are in line with the scenarios of the previous study~[Anonymized]. In some threads, reviewers asked contributors to build on existing code instead of adding a copy. Review thus catches duplication at its origin, before it reaches mainline, and the duplication that remains is what escaped review or was tolerated.

Maintainers also took part in choosing the technique. In several series, a maintainer suggested a deduplication that the contributor had not proposed, such as parameterizing a function repeated several times or reusing an implementation already available in the kernel, as also happened in C19 and C20. Consequently, a contributor does not need to identify the right technique beforehand, since the review can point to it.

In summary, the mailing lists showed the same short list of basic techniques, led by Extract Function, in subsystems we did not observe, with maintainers helping to choose the technique. The lists show the same short set of basic techniques in subsystems we did not observe.

\section{Concluding Remarks}\label{sec:conclusion}

In this study, we examined how duplication debt is repaid in the Linux kernel, combining participant observation with the analysis of deduplication contributions mined from the kernel mailing lists.
Our results show that, despite the kernel's rigorous review process, deduplication opportunities remain in the code and can often be addressed with simple refactoring techniques, and that maintainers are more receptive when these refactorings reuse abstractions already available in the kernel.
These opportunities are therefore a suitable entry point for contributors with less experience in the kernel.

We raise two hypotheses for why such simple duplications persist. First, since review on the mailing lists centers on the changes proposed in each patch, it may be difficult for maintainers to notice that new code duplicates code already present elsewhere in the kernel. Second, in terms of the principal and interest of technical debt~\cite{seaman2011measuring}, that is, the effort required to pay off a debt and the extra effort incurred while it remains unpaid, these duplications seem to have a low principal, since simple techniques remove them, and possibly a low interest in the short term, since their cost only materializes when one of the copies needs to change. Debt with low interest tends to be a low priority for maintainers, who may leave it in the code, where its low principal allows contributors who are not maintainers to repay it.
