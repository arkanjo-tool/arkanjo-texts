\begin{abstract}
Code duplication is a well-known source of technical debt, but little is known about how developers of large, long-lived systems actually pay it back. We investigate code deduplication in the Linux kernel, where changes are publicly reviewed on mailing lists before they reach the upstream repository (mainline). Our goal is to understand how clones are refactored in practice, which refactoring techniques developers apply, and how maintainers receive deduplication patches. We combine two sources of evidence. First, through an ethnographic study, we submitted deduplication patches to the AMDGPU and IIO subsystems and followed their review process. We qualitatively analyzed 30 contributions, classifying the refactoring techniques applied and discussed with maintainers according to Fowler's refactoring catalog. Among our findings, we highlight that maintainers tend to resist deduplications that introduce new abstractions more than the reuse of existing ones. Second, we mined patches from the mailing lists for clone refactorings arriving in a sample of 71 contributions; we quantitatively analyzed the techniques applied to validate and expand the findings from our ethnographic study. Extract Function was the most frequent technique in both datasets, suggesting that even simple refactoring techniques can yield valuable contributions to a system as complex as the Linux kernel. By analyzing 101 contributions, this study provides empirical evidence of the refactoring techniques used to remove code duplication in the Linux kernel, bringing insight on how these techniques relate to the acceptance of deduplication during its review process.
\end{abstract}

\section{Introduction}\label{sec:introduction}

Developers often reuse existing code by copying, pasting, and adapting it, a practice that accompanies the evolution of large, long-lived systems~\cite{kumar2016bigclones}. The resulting duplication is a well-known code smell~\cite{fowler2018refactoring} and, as such, a form of technical debt~\cite{kruchten2012technical}, whose cost is paid during maintenance. A change to one copy, such as a bug fix, must be propagated to all the others, and inconsistent changes to clones that should evolve together are a known source of faults~\cite{juergens2009clones}.

Linus's Law states that ``given enough eyeballs, all bugs are shallow''~\cite{raymond1999cathedral}.
In the Linux kernel, part of this examination takes place in a well-established and rigorous review process, in which patches are publicly reviewed on mailing lists before integration and only about a third of them are eventually accepted~\cite{jiang2013patch}.
Extending this reasoning to technical debt, such a process would also be expected to catch duplicated code before it is merged, leaving few opportunities for simple deduplication.
This expectation, however, does not seem to hold, as duplicated code, from small fragments to entire files and directories, is still found in the kernel~\cite{kumar2016bigclones}.

In this context, we investigate how duplication debt is repaid in practice in the Linux kernel, examining which refactoring techniques developers use to remove clones and how maintainers respond to deduplication patches during review.
To this end, we draw on two sources of evidence.
First, we conducted an ethnographic study based on participant observation in the AMDGPU and IIO subsystems, in which we submitted deduplication patches ourselves and also followed the review of patches submitted by students during a university course. We qualitatively analyzed these 30 contributions, classifying, according to Fowler's refactoring catalog~\cite{fowler2018refactoring},  the techniques they applied. Second, we mined the kernel mailing lists for clone refactorings, using a broad regular expression over duplication-related keywords that retrieved 207 threads, which we manually analyzed to retain only those actually concerned with code duplication, resulting in 71 contributions. We then quantitatively analyzed the refactoring techniques applied in these contributions, using the same catalog, to validate and expand the findings of the ethnographic study.

In the ethnographic study, maintainers were more reluctant to accept deduplications that introduced new abstractions than those that reused abstractions already available in the kernel.
In both sources, Extract Function was the most frequently applied technique. These findings suggest that deduplication is a suitable entry point for contributors with less experience in the kernel, since, although it requires understanding the duplicated code and its context, it involves relatively low complexity and can often be addressed with simple refactoring techniques. They also indicate that, despite its rigorous review process, the Linux kernel still carries duplication debt that is cheap to repay. With this study, we aim to draw attention to the duplication debt that remains to be repaid in the Linux kernel and to offer insights into how it can be addressed.

\section{Related work}\label{sec:related_work}

Wang and Godfrey~\cite{wang2014intentional} searched Linux kernel commit messages for ``duplicated code'' and found that these intentional clone refactorings account for fewer than 1\% of the clone changes detected in four subsystems. Choi et al.~\cite{choi2012clones} examined how clones are refactored by comparing versions of three open-source Java projects, and found that refactored clone pairs were mostly handled with two patterns from Fowler's catalog, Replace Method with Method Object and Extract Method. Unlike these studies, which infer clone refactorings from commit messages or code versions, we examine deduplication patches together with their review, both from within the community, by submitting and following patches, and on the kernel mailing lists, where the complete discussion of each contribution is available rather than only its commit message.


Other studies proposed ways of reducing duplication in the kernel.
Kadav and Swift~\cite{kadav2012drivers} found that 8\% of driver code is very similar to other driver code and suggested procedural abstraction, better support for multiple chipsets, and table-driven programming to reduce it. Yu and Ramaswamy~\cite{yu2008modularity} classified 903 clone sets into three categories and suggested library functions, aspects, or no change, depending on the category. Kumar et al.~\cite{kumar2016bigclones} represented duplicated files and directories as templates in a layer above the code, reducing redundant code by 30--50\% in the groups they studied. These techniques were proposed by researchers who analyzed the code from the outside, and none of these studies reports submitting the changes to kernel maintainers. In contrast, we study techniques applied in real patches submitted to kernel maintainers.

Arcanjo et al.~\cite{arcanjo2026repeat} submitted deduplication patches to the AMDGPU and IIO subsystems and, from 13 patch series, identified four factors under which maintainers tolerate duplication, namely driver-forking, readability, integration overhead, and performance.
In that study, the refactoring used in each contribution appears only as part of the account of each review, without being characterized or compared. We follow the same participant observation approach and expand the sample to 30 contributions, focusing on the techniques they apply and on how maintainers receive them.
We also analyze contributions from the kernel mailing lists, to check whether the same techniques appear or whether new ones emerge.



\section{Methodology}\label{sec:methodology}

To understand how code duplication is removed in the Linux kernel, we combined two complementary sources of evidence. Through participant observation, we followed deduplication patches from their submission through their discussion with maintainers, which gave us an in-depth view of how these contributions are received. Through mining the kernel mailing lists, we collected deduplication contributions beyond those we followed, which allowed us to check whether the techniques observed in the first source also appear in a broader sample. We then classified the refactoring techniques in both samples according to Fowler's catalog~\cite{fowler2018refactoring}, analyzing the first qualitatively and the second quantitatively. The following subsections describe each of these steps in detail.

\subsection{Participant Observation}\label{subsec:participant-observation}

We adopted an ethnographic approach to observe how deduplication patches are received from within the kernel community, following each decision as it happens rather than reconstructing it afterwards from code artifacts.
We conducted this participant observation in the IIO and AMDGPU subsystems of the Linux kernel, adopting two of the observer roles described by Gold~\cite{gold1958roles}, complete participant and participant as observer. In both roles, the duplications addressed by the patches were identified with ArKanjo~\cite{arcanjo2025arkanjo}, a tool for detecting function-level code duplication in the Linux kernel. We consider each patch series, including all its versions, as one contribution.
In total, we qualitatively analyzed 30 contributions, 13 of which had been analyzed in a previous study~\cite{arcanjo2026repeat} (C1 to C13) and 17 of which are new (C14 to C30), all listed in Table~\ref{lbl:patches-summary}.

In the complete participant role, we contributed to the kernel ourselves, selecting duplications reported by the tool, preparing deduplication patches, submitting them to the subsystem mailing lists, and interacting with maintainers during review, which resulted in 6 of the 17 new contributions.

In the participant as observer role, we followed contributions submitted by students during a university course in the first semester of 2026.
We mentored them during the submission process and followed the reviews they received from maintainers. The students submitted the remaining 11 new contributions.


\subsection{Mailing Lists Mining} 

To check whether the techniques observed in the participant observation also appear in contributions beyond those we followed, we mined e-mails from the kernel mailing lists available in the LKML5Ws dataset~\cite{passos2026lkml5ws}.
We used four lists, IIO, AMDGPU, IOMMU, and I2C.

Since the dataset stores individual e-mails, we first reconstructed the discussion threads, linking each e-mail to its parent through the \texttt{In-Reply-To} header, falling back to the last identifier in the \texttt{References} header when \texttt{In-Reply-To} was missing or pointed to a message absent from the dataset.
We then grouped the linked e-mails into threads,  and ordered the messages of each thread by date.

Based on the vocabulary that contributors and maintainers used to discuss duplication during the participant observation, we built a regular expression to filter threads. Among the threads that matched it, we randomly selected 220 threads. 13 threads were excluded, 11 that contained only pull requests, which summarize patches discussed in other threads and include neither diffs nor discussion, 1 that was already part of another thread in the sample, and 1 whose duplication terms appeared only in text quoted from other messages, leaving 207 threads.

Two authors independently labeled each of the 207 threads as related or not to code duplication, and resolved disagreements by consensus. This resulted in 71 threads related to code duplication, 25 from IOMMU, 18 from AMDGPU, 15 from IIO, and 13 from I2C, which form the sample we analyzed.

We classified the 30 patch series for code deduplication according to the refactoring techniques they apply, using Fowler's 
catalog~\cite{fowler2018refactoring}. Five techniques appear in our corpus (Table~\ref{lbl:patches-summary}): Extract Function is the most frequent,
applied in 10 patch series, followed by Parameterize Function with 6, Substitute Algorithm with 5,
Replace Inline Code with Function Call with 4, and Pull Up Method with 3.
All five techniques are well-known entries of Fowler's catalog, which suggests that deduplication
can be addressed without complex refactorings.
These techniques differ in whether they reuse code that already
exists in the kernel or introduce a new abstraction, and in where the shared code is placed. In the 
following subsections, we describe how each group of techniques is applied in the kernel and how code 
review shaped the final form of the submissions.

Most contributions were small. The median contribution removed $31$ lines of code, and 27 of the 30
removed fewer than $100$. Three contributions (C9, C11, and C29) even added between $1$ and $4$ lines.
Size did not determine how a contribution was received: the three largest ones (C1, C2, and C17,
each with more than $390$ lines removed) were all accepted, and C17 was accepted in its first version
despite changing $3{,}309$ lines ($+1{,}274$ added, $-2{,}035$ deleted).

\subsection{Reusing and Simplifying Existing Code}\label{subsec:reusing-and-simplifying}

We classified techniques Substitute Algorithm and Replace Inline Code with Function Call 
as those that reuse or simplify existing code. Unlike the techniques in Section~\ref{subsec:new-abstractions}, 
they remove the duplication without adding a new layer to the code. Of the 30 patch series, only 9 fall into 
this group, that is, about 30\%.

When the duplicated function already exists in another hardware version, the reuse happens through
the function pointer tables that each version uses to register its callbacks. In contribution C20, the contributor found that
\texttt{jpeg\_v3\_0} had an interrupt handler identical to the one in \texttt{jpeg\_v2\_0} and, 
following a maintainer's suggestion, simply pointed \texttt{jpeg\_v3\_0\_irq\_funcs} to the previous version's
function, removing the duplicate. In this case, no new code is needed.

In the Substitute Algorithm patch series, the duplicated code was usually a sequence of \texttt{switch} cases that mapped 
values in a very similar way. Contributions C13, C17, and C23 replaced these \texttt{switch} cases 
with lookup tables, so the mapping is described as data instead of control flow. However, this change is 
not always seen as an obvious improvement. In contribution C23, a maintainer questioned whether the new table 
was really less prone to errors and concluded that the advantage was ``rather the reduction in verbosity''. 
Thus, a lookup table is accepted when it makes the mapping easier to read, as in C23, but C13 was 
rejected because the maintainer judged that the code reduction did not compensate for the loss of 
readability, which is directly related to scenario (T2)~\cite{arcanjo2026repeat}.

\subsection{Introducing New Abstractions}\label{subsec:new-abstractions}

The remaining techniques, Extract Function, Parameterize Function, and Pull Up Method, are those that 
somehow add a new layer to the code: a new function, a function moved to a shared file, or a more general 
function that combines the duplicated ones through parameters. These techniques were the most common 
in our corpus, with 19 of the 30 patch series, that is, about 63\%.

For Extract Function, the main difference between the two subsystems is where the extracted function is placed. 
In the IIO contributions C4, C10, and C11, the duplicated functions belonged to the 
same driver, and the common function stayed in the same file. In AMDGPU, all Extract Function patch series dealt 
with functions duplicated across different hardware versions, a consequence of the driver forking (T1) practice already 
observed in the subsystem~\cite{arcanjo2026repeat}. In these cases, the common function was moved to a generic layer shared by
all hardware versions, such as \texttt{amdgpu\_gfx.c} (contributions C21, C22, and C27) and \texttt{amdgpu\_gmc.c} (contributions C25 and C26), or to a 
proposed new file (C18). This shows that, in AMDGPU, extracting a function also means choosing a place for it in the driver 
architecture, and, as discussed in Section~\ref{subsec:how-review-reshapes-the-refactoring}, new files proposed by the 
patch series were removed during review.

Being identical, however, is not enough for a function to be moved to the generic layer. In contribution C22, the 
maintainers agreed that there was nothing specific to the hardware generation in the function and recognized 
that it was ``probably just copy and pasted over when we brought up gfx12''. In contribution C25, the duplicated functions 
were also identical, but the maintainer stated that they were intentionally kept separated for each generation. 
In practice, what decides if the code can be shared is whether its behavior belongs to a single hardware generation 
or to all of them, which the textual similarity alone does not show.

Parameterize Function appeared only in IIO, and how the parameter is added matters. 
In contribution C6, the two functions differed only in the type of \texttt{struct} they used, and the contributor passed a 
generic \texttt{struct} as a parameter, which was accepted. In C29, the common function received a 
boolean parameter (\texttt{is\_accel}) and several levels of pointers, and a maintainer replied: ``Here and below 
the function is completely uglified. Even kernel documentation suggests to avoid bool parameters like this.'' 
In C9, the parameter forced the reader to look both at the function and at where the value was 
set~\cite{arcanjo2026repeat}. Both series were rejected for readability reasons (T2).

Pull Up Method differs from Extract Function in how much of the duplicated code becomes shared. 
In Extract Function, only part of a function becomes a new shared function, whereas in Pull Up Method the 
whole duplicated function is moved to a shared place. Contribution C2 illustrates this technique in the AMDGPU 
display code, where the \texttt{hpd\_ack()} function was duplicated, with minimal changes, in the drivers of 
several GPU generations. Instead of extracting parts of these copies, the contributor replaced them with two library 
functions that covered all cases, so that each generation calls the shared implementation instead of keeping 
its own copy.

\subsection{How Review Reshapes the Refactoring}\label{subsec:how-review-reshapes-the-refactoring}
% Talvez falar sobre o baixo numero de patches da categoria "Reusing and Simplifying Existing Code": 
% Talvez seja necessário ter um maior conhecimento do subsistema para fazer um INLINE_FUNCTION e um REPLACE_INLINE
A recurring pattern across some contributions is that maintainer review
can redirect a patch, changing the abstraction scope, the refactoring
technique, or both. Three contributions illustrate each of these outcomes.

In C18, the first version consolidated the duplicated functions into a new 
file, \texttt{amdgpu\_common.c}, intended to group functions shared across 
the subsystem. A maintainer rejected this layout: ``Please don't when they 
are functional identical then move them a layer up instead of messing up the 
backends.'' He then argued that each function would fit better in a 
different, already existing layer. Although the refactoring technique 
remained the same across all revisions, the abstraction scope shifted to 
follow the layering conventions already established in the subsystem.

In C27, the opposite happened. The scope was kept, but the technique 
changed. The contributor initially proposed a single generic function in 
\texttt{amdgpu\_gfx.c} to replace \texttt{gfx\_v11\_0\_handle\_priv\_fault} 
and \texttt{gfx\_v12\_0\_handle\_priv\_fault}, arguing that the two were 
identical. In the first review, a maintainer pointed to a specific code 
fragment and noted ``Even when they are identical on gfx11 and gfx12 this 
decoding here is HW specific and doesn't belong here''. The target layer was 
not questioned, and \texttt{amdgpu\_gfx.c} remained the destination across 
all revisions. As a result, the contributor switched from Pull Up Method to Extract Function. Therefore, only 
the generation-independent part was moved to \texttt{amdgpu\_gfx.c}, while 
the hardware-specific decoding remained in each generation's own function.

In C19, review changed both the scope and the technique. The first version 
made \texttt{jpeg\_v5\_0\_1.c} and \texttt{jpeg\_v5\_0\_2.c} share a common 
interrupt routine placed in a new file, \texttt{jpeg\_v5\_0\_interrupt.c}. 
This proposal was rejected in the first review because the routine was not 
common to the whole family and the maintainer pointed ``This is not common to 
jpeg v5. jpeg\_v5\_0\_0.c has a different interrupt handler''. The maintainer then 
suggested a narrower alternative: ``I would just make the implementation in 
jpeg\_v5\_0\_1.c non-static and then just use it directly in 
jpeg\_v5\_0\_2.c''. The duplication was still removed, but the scope was 
changed from a family-wide file to the two drivers that actually share the 
behavior, and the technique changed accordingly, to Replace Inline Code with Function Call.

Although the outcomes are different, the main concern is the same in all three cases. 
The shared code either did not belong to the proposed layer or
did not apply uniformly to every component that layer serves. These cases do
not fit the four takeaways proposed in previous study~\cite{arcanjo2026repeat}. 
However they relate to T1, since the objections derive from hardware-specific code, 
the maintainers did not defend the duplication itself, nor did they invoke 
readability (T2), integration overhead (T3), or performance (T4). This leads to the 
fifth takeaway:

\begin{framed}
\textbf{Takeaway T5 (Abstraction Scope):} Maintainers may reject or redirect
a deduplication when the duplicated code does not share an appropriate
abstraction boundary. Consolidating such code into a shared layer can be
considered inappropriate when the behavior does not apply uniformly to every
component that the layer serves.
\end{framed}
