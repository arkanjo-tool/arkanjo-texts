\begin{abstract}
Code duplication is a well-known source of technical debt, but little is known about how developers of large, long-lived systems actually pay it back. We investigate code deduplication in the Linux kernel, where changes are publicly reviewed on mailing lists before they reach the upstream repository (mainline). Our goal is to understand how clones are refactored in the Linux kernel, which refactoring techniques developers apply, and how maintainers receive deduplication patches. We combine two sources of evidence. First, in an ethnographic study, we submitted deduplication patches to the AMDGPU and IIO subsystems and followed their respective review processes. We qualitatively analyzed 30 contributions, classifying the refactoring techniques applied and discussed with maintainers. Among our findings, we highlight that maintainers tend to resist deduplication that introduces new abstractions more than the reuse of existing ones. Second, we mined patches from the kernel mailing lists to identify clone refactorings across a sample of 71 contributions related to code duplication. We quantitatively analyzed the techniques used and compared them with the findings from our ethnographic study. By analyzing 101 real contributions, this study provides empirical evidence of how duplication debt is managed in the Linux kernel, offering insight into deduplication patches as, for instance, entry points for contributors.
\end{abstract}

\section{Introduction}\label{sec:introduction}

Developers often reuse existing code by copying, pasting, and adapting it, a practice that accompanies the evolution of large, long-lived systems~\cite{kumar2016bigclones}. The resulting duplication is a well-known code smell~\cite{fowler2018refactoring} and, as such, a form of technical debt~\cite{kruchten2012technical}, whose cost is paid during maintenance. A change to one copy, such as a bug fix, must be propagated to all the others, and inconsistent changes to clones that should evolve together are a known source of faults~\cite{juergens2009clones}.

Linus's law states that \textit{``given enough eyeballs, all bugs are shallow''}~\cite{raymond1999cathedral}.
In its birthplace, the Linux kernel, this law manifests as a well-established and rigorous review process, in which contributions (called \textit{patches}) are publicly reviewed on mailing lists before integration~\cite{linux_process_mailinglist}, and only about a third are accepted~\cite{jiang2013patch}.
Extending this reasoning to technical debt, such a process would also be expected to catch, for instance, duplicated code before it is merged, leaving few opportunities for simple deduplication.
This expectation, however, does not seem to hold, as duplicated code, from small fragments to entire files and directories, is still found in the kernel~\cite{kumar2016bigclones}.

In this context, we investigate how the Linux community manages duplication debt by examining how it attributes the \textit{interest} and \textit{principal}~\cite{seaman2011measuring} of code clones and proposed repayments.
To this end, we draw on two sources of evidence.
First, we conducted an ethnographic study in the AMDGPU and IIO subsystems, in which we submitted 30 deduplication patches and followed their review process. For each, we qualitatively analyzed and classified the techniques applied according to Fowler's refactoring catalog~\cite{fowler2018refactoring}. Second, we mined the kernel mailing lists, filtering for clone refactorings, resulting in the selection of 71 threads. We then quantitatively analyzed the refactoring techniques applied, using the same catalog, to validate and expand on the ethnographic study's findings.

From our results, we highlight: (1) duplication debt is present throughout the Linux project and often explicitly acknowledged by the community; (2) maintainers were more reluctant to accept repayments that introduced new kernel abstractions than those that reused existing ones; and (3) basic refactoring techniques, like \textit{Extract Function}, were the most applied in accepted repayments.
Among other results, these findings suggest that, despite the rigorous review process, duplication debts with low principal and low interest that are reasonably cheap to repay exist for different reasons, e.g., the distributed nature of the project, the need to foster new contributors, and the prioritization of repayments. In this sense, a suitable entry point for contributors with less experience in the kernel is deduplication patches, which can often be addressed with simple refactoring techniques and are valuable to the Linux community.

With this study, we aim to draw attention to the management of duplication debt that remains to be repaid in the Linux kernel and to offer insights into how it can be addressed.


\section{Related work}\label{sec:related_work}

Wang and Godfrey~\cite{wang2014intentional} searched Linux kernel commit messages for \textit{``duplicated code''} and found that these intentional clone refactorings account for fewer than 1\% of the clone changes detected in four subsystems. Choi et al.~\cite{choi2012clones} examined how clones are refactored by comparing versions of three open-source Java projects, and found that refactored clone pairs were mostly handled with two patterns from Fowler's catalog, \textit{Replace Method with Method Object} and \textit{Extract Method}. Unlike these studies, which infer clone refactorings from commit messages or source code versions, we examine deduplication patches alongside their reviews by submitting and following patches on the kernel mailing lists, where the complete discussion that generated the integrated code is available.

Other studies proposed ways of reducing duplication in the kernel.
Kadav and Swift~\cite{kadav2012drivers} found that 8\% of driver code is very similar to other driver code and suggested procedural abstraction, better support for multiple chipsets, and table-driven programming to reduce it. Yu and Ramaswamy~\cite{yu2008modularity} classified 903 clone sets into three categories and suggested library functions, aspects, or no change, depending on the category. Kumar et al.~\cite{kumar2016bigclones} represented duplicated files and directories as templates in a layer above the code, reducing redundant code by 30--50\% in the groups they studied. These studies do not report submitting the techniques to the community or engaging in the review process to gauge practitioners' perspectives. In contrast, we study techniques applied in real patches submitted to the kernel mailing lists.

In our previous study~[x], we submitted deduplication patches to the AMDGPU and IIO subsystems and, from 13 patch series, identified four scenarios under which maintainers tolerate duplication: driver-forking, readability, integration overhead, and performance. In that study, the refactoring used in each contribution appears only as part of each review's account, without being characterized or compared. We follow the same participant-observation approach, yet expand the sample to 30 contributions, focusing on the techniques they employ and how the community receives them. Additionally, we cross-check our findings against contributions from the kernel mailing lists to determine whether the same techniques appear or new ones emerge.

\section{Methodology}\label{sec:methodology}

To understand how duplication debt is managed in the Linux kernel, we combined two complementary sources of evidence. Through participant observation, we followed deduplication patches from their submission via their discussion with the community, which gave us an in-depth view of how these contributions are received. By mining the mailing lists, we collected deduplication contributions beyond those we had followed, which allowed us to check whether the techniques observed in the first source also appeared in a broader sample. We then classified the refactoring techniques in both samples according to Fowler's catalog~\cite{fowler2018refactoring}, analyzing the first qualitatively and the second quantitatively. The following subsections describe each of these steps in detail.

\subsection{Participant Observation}\label{subsec:participant-observation}

We adopted an ethnographic approach to observe how deduplication patches are received from within the kernel community, following each decision as it happened rather than reconstructing it afterward from merged code artifacts.
Participant observation was conducted in the IIO and AMDGPU subsystems of the Linux kernel by playing two of the observer roles described by Gold~\cite{gold1958roles}: complete participant and participant-as-observer. In both roles, the duplications addressed by the patches were identified with Anonymous Tool~[x], a tool for detecting function-level code duplication in the Linux kernel. We treat all versions of each patch series as a single contribution.
In total, we qualitatively analyzed 30 contributions, 13 submitted in 2025 (labeled C1 to C13) and 17 in 2026 (labeled C14 to C30).

In the complete participant role, we contributed to the kernel ourselves, selecting duplications reported by the tool, preparing deduplication patches, submitting them to the subsystem mailing lists, and interacting with maintainers during review, a total of 7 of the 30 contributions.
%considerei o patch do Luan como complete e o total de 30 para não confundir.

In the participant-as-observer role, we followed contributions submitted by students during a university course in 2025 and 2026.
We mentored them during the submission process and followed the reviews they received from the community. The students submitted the remaining 23 new contributions.

\subsection{Mailing Lists Mining} 

To check whether the techniques observed in the participant observation also appear in contributions beyond those we followed, we mined e-mails from the kernel mailing lists available in the LKML5Ws dataset~\cite{passos2026lkml5ws}.
We used four lists: IIO, AMDGPU, IOMMU, and I2C.

Since the dataset stores individual e-mails, we first reconstructed the discussion threads, linking each e-mail to its parent through the \texttt{In-Reply-To} header, falling back to the last identifier in the \texttt{References} header when \texttt{In-Reply-To} was missing or pointed to a message absent from the dataset.
We then grouped the linked e-mails into threads and ordered the messages of each thread by date.

Based on the vocabulary that contributors and maintainers used to discuss duplication during the participant observation, we built a regular expression to filter threads. Among the threads that matched it, we discarded those authored or answered by our group or by the course students and randomly selected 220 of the remaining ones. 13 threads were excluded: 11 that contained only pull requests, which summarize patches discussed in other threads and include neither diffs nor discussion, 1 that was already part of another thread in the sample, and 1 whose duplication terms appeared only in text quoted from other messages, leaving 207 threads.

Two authors independently labeled each of the 207 threads as related or not to code duplication, and resolved disagreements by consensus. This resulted in 71 threads related to code duplication, 25 from IOMMU, 18 from AMDGPU, 15 from IIO, and 13 from I2C, which form the sample we analyzed. The labeled threads and the details of the sample selection are available in our replication package (Section~\ref{sec:replication-package}).

\subsection{Refactoring Technique Analysis}\label{sec:technique_analysis}

We classified the refactoring techniques according to Fowler's catalog~\cite{fowler2018refactoring}, beginning with the participant observation contributions. For each of the 30 contributions, we examined the code changes in its patches and compared them with the descriptions and examples of the refactorings in the catalog, assigning the technique that best matched the changes.
We then analyzed these contributions qualitatively, relating the technique applied in each one to how maintainers received it. Next, we applied the same classification to the 71 mailing list contributions. Some of these patch series addressed more than one change, and in these cases we assigned a technique to each change so that a single contribution may account for multiple techniques.
Finally, we analyzed this sample quantitatively, counting how often each technique was applied.

\subsection{Strategies of removing a clone}\label{subsec:reusing-and-simplifying}

The techniques that reuse and simplify existing code, Replace Inline Code with Function Call and Substitute Algorithm, were also the ones most easily accepted: 8 of their 9 contributions were accepted, compared with 9 of the 19 contributions that introduce a new abstraction\footnote{C3 and C24 were not assigned a deduplication technique and are not counted in either group}. We describe the techniques grouped by how they remove the clone: extracting the repeated code, reusing what already exists, substituting the algorithm, and parameterizing similar functions.

Extract Function, the most frequent technique, only requires moving the repeated fragment into a new function and calling it from each copy. In IIO, duplicated functions were part of the same driver, so the new function remained in the same file. In AMDGPU, the copies were spread across hardware versions due to driver-forking, and the new function was placed in a generic layer already shared by these versions, such as \texttt{amdgpu\_gfx.c} and \texttt{amdgpu\_gmc.c}. In C22, this was enough to remove the duplication: the maintainers agreed that nothing in the function was specific to a hardware generation; one of them speculated that it was \textit{``probably just copy and pasted over when we brought up gfx12''}, and accepted the patch series. In C25, the duplicated functions were also identical, but the maintainer stated that they were intentionally kept separated for each generation, and the patch series was rejected. Both duplications derive from driver-forking, but only the first appears to have been accidental. Thus, extracting the function is the simple part of the task, while what requires the contributor's attention is checking whether the duplication was intended.

Extract Function was not always an easy case. C4 was dropped because the new helper was questioned, and the gain was seen as too small to justify the upstreaming effort. The status \texttt{Dropped} therefore covers both explicit rejection and series that have stopped.

Pull Up Method, in turn, moves a whole duplicated function, rather than just a fragment, to a shared place and can remove a large amount of code with a simple change. In C2, the \texttt{hpd\_ack()} function was duplicated, with minimal changes, in the drivers of several GPU generations, a consequence of driver forking, and the contributor replaced these copies with two library functions that covered all cases, which was accepted. In C28, however, the same technique was rejected precisely because of driver-forking: one maintainer initially accepted the patch series, but another dropped it, arguing that keeping the code independent for each generation had avoided problems in the past.

Replace Inline Code with Function Call removes duplication without writing any new code, since the function that replaces the repeated code already exists; the contributor only needs to call it. Noticing that an existing function can replace the repeated code, however, requires some investigation of the subsystem, and maintainers can point it out during review. In C20, the contributor found that the interrupt handler in \texttt{jpeg\_v3\_0} was identical to that in \texttt{jpeg\_v2\_0} and, following a maintainer's suggestion, pointed the newer version's callback table to the older function, removing the duplicate. This duplication is another consequence of driver-forking, as the newer hardware version kept its own copy of a function already implemented for the previous one. In IIO, C12 applied the same technique by replacing duplicated functions with calls to SPI helpers already available in the kernel. The only exception was a single occurrence that reads large buffers, which, at the maintainer's request, continued to use an internal helper since the generic ones would harm performance~[x].

Substitute Algorithm was also simple to apply when the duplicated code consisted of a sequence of \texttt{switch} cases that mapped values in a very similar way. In these cases, the contributor only had to list the values for each case in a lookup table, so the mapping is described as data rather than control flow. In C23, a maintainer questioned whether the new table was really less prone to errors than the \texttt{switch} cases, but concluded that its advantage was \textit{``rather the reduction in verbosity''}, and the patch series was accepted. The same replacement also scales to larger changes; for example, in C17, the largest contribution in our corpus, it was accepted in its first version. Since the gain of this technique comes mostly in readability, the same scenario can also work against it: in C13, the maintainer judged that the code reduction did not compensate for the loss of readability, and the patch series was rejected.

Parameterize Function, which appeared only in IIO, merges similar functions into a single function that receives their differences as parameters. Only 2 of the 6 series that used it were accepted. In C6, the functions differed only in the type of \texttt{struct}, so a generic \texttt{struct} was passed as a parameter, and the patch was accepted in its first version, also fixing a bug. The dropped series were questioned on readability and gain rather than on correctness. In C5, a maintainer judged that the reduction was not significant enough to justify the more complex code. In C9, the main objection was that wrapping the code scattered what used to be close together, so the reviewer had to look at the function and at where the value was set. In C29, the common function received a boolean parameter (\texttt{is\_accel}) and several levels of pointers, and a maintainer replied: \textit{``Here and below the function is completely uglified. Even kernel documentation suggests to avoid bool parameters like this''}. Another maintainer noted that a deduplication that adds lines, as C29 did, should be questioned. In our cases, parameterizing worked when the parameter captured the only difference between the functions, as in C6, and not when it became a flag or shifted the point at which the behavior is decided away from the reader.

Overall, the techniques we observed are well known and result in localized changes. What the reviews add is why a clone was not removed: it was kept on purpose, the result would be harder to read, the gain did not justify the integration effort, or the shared code would sit on a performance-sensitive path. These scenarios are not fixed rules, since maintainers of the same subsystem disagreed on them, as in C28.

Moreover, code review often reshapes the refactoring itself, showing how the maintainers' knowledge of the subsystem can influence the final form of a contribution.

\subsection{How Review Reshapes the Refactoring}\label{subsec:how-review-reshapes-the-refactoring}
% Talvez falar sobre o baixo numero de patches da categoria "Reusing and Simplifying Existing Code": 
% Talvez seja necessário ter um maior conhecimento do subsistema para fazer um INLINE_FUNCTION e um REPLACE_INLINE
A recurring pattern across some contributions is that maintainer review can redirect a patch, changing the abstraction scope (a new duplication scenario we identified in this study, completing our previous work~[X]), the refactoring technique, or both. Three contributions illustrate each of these outcomes.

In C18, the first version consolidated the duplicated functions into a new file, \texttt{amdgpu\_common.c}, intended to group functions shared across the subsystem. A maintainer rejected this layout: \textit{``Please don't when they are functional identical then move them a layer up instead of messing up the backends.''} He then argued that each function would fit better in a different, already existing layer. Although the refactoring technique remained the same across all revisions, the scope of abstraction shifted to align with the layering conventions already established in the subsystem.

In C27, the opposite happened. The scope was kept, but the technique changed. The contributor initially proposed a single generic function in \texttt{amdgpu\_gfx.c} to replace \texttt{gfx\_v11\_0\_handle\_priv\_fault} and \texttt{gfx\_v12\_0\_handle\_priv\_fault}, arguing that the two were identical. In the first review, a maintainer pointed to a specific code fragment and noted \textit{``Even when they are identical on gfx11 and gfx12 this decoding here is HW specific and doesn't belong here''}. The target layer was not questioned, and \texttt{amdgpu\_gfx.c} remained the destination across all revisions. As a result, the contributor switched from Pull Up Method to Extract Function. Therefore, only the generation-independent part was moved to \texttt{amdgpu\_gfx.c}, while the hardware-specific decoding remained in each generation's own function.

In C19, the review changed both the scope and the technique. The first version made \texttt{jpeg\_v5\_0\_1.c} and \texttt{jpeg\_v5\_0\_2.c} share a common interrupt routine placed in a new file, \texttt{jpeg\_v5\_0\_interrupt.c}. This proposal was dropped in the first review because the routine was not common to the whole family, and the maintainer pointed out that \textit{``This is not common to jpeg v5.  \texttt{jpeg\_v5\_0\_0.c} has a different interrupt handler''}. The maintainer then suggested a narrower alternative: \textit{``I would just make the implementation in \texttt{jpeg\_v5\_0\_1.c} non-static and then just use it directly in \texttt{jpeg\_v5\_0\_2.c}''}. The duplication was still removed, but the scope was narrowed from a family-wide file to the two drivers that actually exhibit the behavior, and the technique was changed accordingly to Replace Inline Code with Function Call.

Although the outcomes are different, the main concern is the same in all three cases. The shared code either did not belong to the proposed layer or did not apply uniformly to all components the layer serves. These cases do not fit the four scenarios proposed in the previous study~[x]. Even though they are adjacent to the driver-forking scenario, the maintainers did not defend the drivers' independence as such, because the objections stem from hardware-specific code. In C19 and C27, code that looked identical was not shared knowledge: another driver of the family has a different handler, and part of the decoding is hardware-specific. In C18, the objection concerned which existing layer should hold the code. Nor did the maintainers invoke readability, integration overhead, or performance. This leads to a \textbf{new scenario}: maintainers may reject or redirect a deduplication when the duplicated code does not share an appropriate abstraction boundary. Consolidating such code into a shared layer may be inappropriate when the behavior does not apply uniformly across all components the layer serves.

\subsection{Deduplication in Other Kernel Contributions}\label{subsec:lore-techniques}

To validate and expand the findings of our participant observation, we identified the refactoring techniques applied in the mailing lists related to code duplication. Since a patch series may apply more than one technique, we count applications of techniques rather than series.
Fig.~\ref{fig:refactoring-heatmap} compares the share of each technique among these applications with the share among our submissions, showing whether the techniques observed in our 30 contributions also appear beyond the ones we followed and which new ones emerge.

Extract Function was the most frequent technique overall in both datasets, accounting for a third of the applications in our corpus and remaining the most common in the mailing lists. The techniques used in our submissions also accounted for most of the applications in the broader sample, including those related to the IOMMU and I2C subsystems, for which we did not submit patches.
The mailing lists also revealed techniques that none of our submissions applied, namely \textit{Remove Dead Code}, \textit{Pull Up Field}, and \textit{Slide Statements}. Pull Up Field moves fields repeated across structures to a shared one. Remove Dead Code was used both for unused code and for implementations that became redundant after equivalent functionality was made available elsewhere in the kernel, such as in a core layer.
%ArKanjo reports function-level clones, so changes to fields and statements fall outside its reach; in some cases, they appear as preparatory steps for a later extraction.

Series without a catalog technique show that deciding whether to remove duplication is part of the task. Some introduced shared code to prevent future duplication rather than to remove an existing clone, and others tolerated duplication across distinct drivers, where abstracting would cost more than it would gain. In other cases, maintainers prevented duplication at the source by asking the contributor to build on an existing driver rather than add a new one. These cases are consistent with the scenarios in the previous study~[x].

In some threads, reviewers asked contributors to build on existing code rather than add a copy. Review thus catches duplication at its origin, before it reaches mainline, and the duplication that remains is what escaped review or was tolerated.
Maintainers also took part in choosing the technique. In several series, a maintainer suggested a deduplication that the contributor had not proposed, such as parameterizing a function repeated several times or reusing an implementation already available in the kernel, as also happened in C19 and C20. Consequently, a contributor does not need to identify the right technique beforehand, since the review can point to it.

In summary, the mailing list mining showed the same set of basic techniques with similar recurrences in subsystems we did not observe, and maintainers helping to choose the technique.

\section{Concluding Remarks}\label{sec:conclusion}

In this study, we examined how duplication debt is repaid in the Linux kernel by combining participant observation with analysis of deduplication contributions mined from the kernel mailing lists.
Our results show that, despite the kernel's rigorous review process, deduplication opportunities remain in the code and can often be addressed with simple refactoring techniques, and that maintainers are more receptive when these refactorings reuse abstractions already available in the kernel.

These opportunities are therefore a suitable entry point for contributors with less experience in the kernel.
We raise three hypotheses, which are not mutually exclusive, as to why such simple duplications persist. First, since the review process centers around a particular development context, it may be difficult for maintainers to notice that new code duplicates code already present elsewhere in the kernel. Second, localized duplications of low interest tend to be low priority, since their cost only materializes when one of the copies needs to be changed. Third, duplications with low principal and low interest are real, actionable potential patches that can foster new contributors without seriously degrading code quality if they are not paid.
